# Spec: Add Cloudflare, Hetzner and DigitalOcean providers

## Design

Follow the existing provider pattern in `AGENTS.md` ("Adding a provider"). Three new providers: `cloudflare`, `hetzner` and `digitalocean`.

### 1. Files per provider

```
modules/<p>/devenv.nix     # packages + enterTest
modules/<p>/mcp.json       # omitted for hetzner (no official server)
modules/<p>/agents.md      # AGENTS.md section: skill, login/tokens, MCP
skills/<p>/SKILL.md
skills/<p>/references/{architecture,security,cli-cheatsheet,terraform,mcp}.md
templates/<p>/             # generated by `nix run . -- <p> --into templates/<p>`
```

Shared files that change:
- `flake.nix`: the `providers` list.
- `.github/workflows/ci.yml`: the matrix gains `cloudflare`, `hetzner`, `digitalocean` and a combined `aws cloudflare` job.
- `README.md`: the provider tables.
- `pkgs/init.sh`: token-scope warnings only (section 4).

### 2. Packages (nixos-unstable, all free and cached on x86_64-linux and aarch64-darwin)

| Module | Packages | `enterTest` |
|---|---|---|
| cloudflare | `wrangler cloudflared flarectl` | `wrangler --version`, `cloudflared --version`, `flarectl --version` |
| hetzner | `hcloud` | `hcloud version` |
| digitalocean | `doctl` | `doctl version` |

Rejected: `cloudflare-cli` (third party), `packer` (unfree).

### 3. Tokens and secrets: read-only for agents, separate write tokens

These providers use API tokens, not CLI SSO. Each provider therefore gets **two kinds of secret**. MCP configs only ever reference the read-only one, so an agent never receives a write token through `.mcp.json`.

| Provider | Read-only token (MCP / agent) | Deploy token (Terraform / CLI) | How to create the read-only token |
|---|---|---|---|
| Cloudflare | `CLOUDFLARE_READ_TOKEN` | `CLOUDFLARE_API_TOKEN` (Terraform provider and wrangler) | API token from the **"Read all resources"** template, plus `Account Resources: Read` |
| Hetzner | none (no MCP) | `HCLOUD_TOKEN` (hcloud and Terraform) | Project token with **Read** permission for inspection work |
| DigitalOcean | `DIGITALOCEAN_READ_TOKEN` | `DIGITALOCEAN_ACCESS_TOKEN` (doctl and Terraform) | Personal access token with the **Read Only** scope (`api:read`) and an expiry |

All secrets go through the existing agenix scripts: `secret-add NAME`, and `secret-run --only NAME -- <cmd>`.

**Typical agent session:**
- Cloudflare: `secret-run --only CLOUDFLARE_READ_TOKEN -- claude`
- DigitalOcean: `secret-run --only DIGITALOCEAN_READ_TOKEN -- claude`

**Hetzner token names:** `hcloud` and its Terraform provider only read `HCLOUD_TOKEN`. The skill therefore tells users to store a Read token under that name for agent sessions and a Read & Write token as `HCLOUD_TOKEN_RW`, running deploys as `secret-run --only HCLOUD_TOKEN_RW -- env HCLOUD_TOKEN="$HCLOUD_TOKEN_RW" terraform apply`. No script changes are needed.

### 4. MCP servers

**Cloudflare** (`modules/cloudflare/mcp.json`):
```json
{
  "mcpServers": {
    "cloudflare-docs": { "type": "http", "url": "https://docs.mcp.cloudflare.com/mcp" },
    "cloudflare-api": {
      "command": "npx",
      "args": ["-y", "mcp-remote@0.14.2", "https://mcp.cloudflare.com/mcp", "--header", "Authorization:${CF_MCP_AUTH}"],
      "env": { "CF_MCP_AUTH": "Bearer ${CLOUDFLARE_READ_TOKEN}" }
    }
  }
}
```

- **`cloudflare-docs`** needs no authentication and is read-only by nature.
- **`cloudflare-api`** is Cloudflare's consolidated API server ("Code Mode", covering about 2,500 endpoints with two tools). It has no server-side read-only mode, so **the token is the boundary**, and the config only references `CLOUDFLARE_READ_TOKEN`.
- **Why the stdio bridge (`mcp-remote`) instead of a direct `type: http` server with `headers`:** Claude Code blanks some credential-like environment variables in remote `url`/`headers`. Stdio `env` isn't affected, so the bridge keeps the token out of the file and works with `secret-run`.
- **Why a token instead of OAuth:** OAuth scopes are chosen interactively and can't be pinned or reviewed in the repo. OAuth stays documented as an alternative.

**DigitalOcean** (`modules/digitalocean/mcp.json`):
```json
{
  "mcpServers": {
    "digitalocean-docs": { "type": "http", "url": "https://docs.mcp.digitalocean.com/mcp" },
    "digitalocean": {
      "command": "npx",
      "args": ["-y", "@digitalocean/mcp@1.0.70", "--services", "accounts,droplets,doks,apps,databases,networking,spaces,volumes,insights"],
      "env": { "DIGITALOCEAN_API_TOKEN": "${DIGITALOCEAN_READ_TOKEN}" }
    }
  }
}
```

- **`--services`** limits the tool surface to infrastructure services. GenAI, marketplace and similar services are left out.
- **No read-only flag exists.** The Read Only token is the boundary.

**Hetzner:** no `mcp.json` file. The init script already skips a missing one. `skills/hetzner/references/mcp.md` explains that there's no official server, lists the community servers with a warning not to use them with write tokens, and points to `hcloud` with a Read token for inspection.

**Init warnings** (`pkgs/init.sh`, extending the existing `case`):
- `cloudflare`: "the Cloudflare API MCP server has no read-only mode; store a 'Read all resources' token as CLOUDFLARE_READ_TOKEN."
- `digitalocean`: "the DigitalOcean MCP server has no read-only mode; store a Read Only token as DIGITALOCEAN_READ_TOKEN."

### 5. Skills

Each skill has the same frontmatter rules and size limits as the existing ones. Every claim links to official documentation.

| Skill | `architecture.md` | `security.md` | `terraform.md` |
|---|---|---|---|
| cloudflare | Reference architectures (developers.cloudflare.com/reference-architecture): zones and DNS, WAF, Workers, R2, Tunnels and Zero Trust | API token templates and least privilege, account vs user tokens, never Global API Key | `cloudflare/cloudflare ~> 5.0` (v5 breaking rewrite); R2 remote state via the S3 backend (`endpoints.s3`, `use_path_style`, `skip_*` flags) |
| hetzner | Projects, networks, firewalls, placement groups, load balancers, Kubernetes on Hetzner | Project-scoped Read vs Read & Write tokens, SSH keys, firewalls by default | `hetznercloud/hcloud ~> 1.69`; Hetzner Object Storage S3 backend (semi-verified, marked) |
| digitalocean | Droplets, VPC, cloud firewalls, load balancers, DOKS, App Platform, managed DBs, Spaces | PAT scopes (Full / Read Only / Custom), mandatory expiry, team access | `digitalocean/digitalocean ~> 2.100`; Spaces S3 backend with `use_lockfile` |

Each skill also has a `cli-cheatsheet.md` (wrangler/cloudflared/flarectl, hcloud, doctl) and an `mcp.md` covering the servers above, token setup, and how to opt in to write access. Opting in means putting a write token in the project's own `.mcp.json`, with a warning.

### 6. Unchanged

- `modules/common` (Terraform, lint, secrets).
- The existing providers.
- The init script's composition logic.
- The flake checks.

## Alternatives rejected

- **Cloudflare OAuth (`type: http`, no token) as the default:** scopes are chosen interactively at login, can't be pinned or reviewed in the repo, and don't work in headless or CI sessions. Documented as an option instead.
- **Direct `headers: Authorization: Bearer ${CLOUDFLARE_…}`:** Claude Code may blank credential-like variables in remote headers. That would fail silently.
- **Cloudflare's per-product servers** (bindings, builds, containers, observability, radar and so on): the consolidated API server covers them. Bindings, builds and containers can write. Observability and radar can be added by users.
- **DigitalOcean hosted remote MCP endpoints:** they only accept tokens in headers (no OAuth), so they hit the same header problem. The local stdio server is equivalent.
- **A community Hetzner MCP server:** not an official vendor server, which breaks the repo rule.
- **One shared token per provider:** an agent would receive write access through `.mcp.json`. Separate read-only secrets make that impossible by default.
- **Adding Scaleway or Linode/Akamai:** outside the approved scope.

## Risks

1. **`mcp-remote` isn't a Cloudflare package.** It's a widely used community MCP transport bridge, pinned to 0.14.2. If it breaks, the fallback is a `type: http` server with a differently named header variable, or OAuth. Plan step 0 verifies it works against `mcp.cloudflare.com` with a read-only token.
2. **Token scope depends on the user.** Config can't verify that `CLOUDFLARE_READ_TOKEN` really is read-only. Mitigations: the name, the skill instructions, the init warning, and the `AGENTS.md` section.
3. **Hetzner state backend:** the Hetzner Object Storage S3 settings are only semi-verified (official docs page returned 404). The skill marks them as such.
4. **Cloudflare Terraform provider v5** has breaking changes from v4. The skill must not mix v4 examples in.
5. **CI cost:** 6 more matrix jobs (3 providers × 2 OS), plus the combined job.
6. **`flarectl` token variable:** it reads `CF_API_TOKEN`, not `CLOUDFLARE_API_TOKEN`. The cheatsheet shows the mapping, using the same `env` pattern as the Hetzner write token.

## Verification

1. **Flake:** `nix flake check` passes, covering `templates-fresh` and `skills` for all 10 skills.
2. **Per provider:** `nix run . -- <p> --into $tmp`, then `devenv --override-input cloud path:<repo> test` passes for `cloudflare`, `hetzner` and `digitalocean`.
3. **Combined:** `nix run . -- aws cloudflare` produces a `.mcp.json` with `aws`, `aws-docs`, `terraform`, `cloudflare-docs` and `cloudflare-api`, and `devenv test` passes.
4. **MCP token hygiene:**
   - `jq` confirms every `${…}` reference in the Cloudflare and DigitalOcean `mcp.json` files is a `*_READ_TOKEN`.
   - `modules/hetzner/mcp.json` doesn't exist.
5. **MCP startup:**
   - `@digitalocean/mcp@1.0.70` answers the MCP `initialize` request locally (an invalid token is fine for the handshake).
   - Manual check with a real read-only Cloudflare token: `cloudflare-api` connects, a read works, and a write is refused by the API.
6. **CI:** green on Linux for the new matrix entries. macOS stays informative.
7. **Skills:** every `SKILL.md` and reference links official documentation, and none uses a v4 Cloudflare provider example.
